## 1. 요약

- **결론**: 운영 환경의 최소 권한 설계는 **IaC가 전제**예요. IaC가 없는 동안은 **CMP를 StackSets로 배포하고 SCP로 보호하는 방식**으로 대체해요.
- **정책 우선순위**: 관리형(ViewOnly/ReadOnly)을 기본으로 깔고 → 쓰기 권한은 CMP로 → 예외는 인라인으로. 같은 인라인이 2~3개 권한세트에서 쓰이면 CMP로 바꿔요.
- **보안 관련 권한(Secrets Manager/KMS)**: 운영 환경에서는 **상시 권한을 빼고 승인 기반 JIT**로 줘요. KMS는 태그 기반(ABAC) 대신 **키 리소스 단위**로 범위를 정해요.
- **고객에게 전할 메시지**: ① IaC는 운영 환경 권한 설계의 핵심 축이다 ② 최소 권한은 한 번 설계하고 끝나지 않고 계속 운영해야 한다.
- **회의 후 확인된 이슈**: 현재 Admin 권한은 11월 말까지 승인돼 있고 12월부터 개편안이 적용될 예정이에요(확정 여부는 확인 필요). TA의 편의성 요구와 고객 매니저의 협력사 통제 요구가 충돌하고 있어 **고객 의사결정이 필요**해요.

## 2. 배경

- SKT는 IAM 권한세트를 **클라우드 포탈로만** 부여해요. 포탈의 권한세트를 표준화하고 개발자 대상 부여 절차를 쉽게 만들기 위한 초기 설계를 진행하고 있어요.
- **As-Is**
  - 권한세트 대부분이 인라인 정책이거나 AdministratorAccess 같은 관리자 수준 관리형 정책이에요. 그래서 변경 관리가 어려워요.
  - 관리자 권한세트에 KMS와 Secrets Manager 같은 보안 서비스 권한이 모두 들어 있어요.
- **To-Be 방향**: 관리형 → CMP → 인라인 순서로 정책을 구성해요.
- **고객 환경**
  - Control Tower 기반 멀티 계정이에요.
  - IaC는 아직 쓰지 않아요. 테라폼으로 CMP를 관리하는 방안은 검토 단계예요.
  - 이 작업에 보안팀이 관여하지 않아요.

## 3. 주요 논의 내용

### 3.1 IaC 여부: 운영 환경 권한 설계의 핵심 전제

- 운영 환경에 쓰기·수정 권한이 있다는 것 자체가 리스크예요(운영 장애 가능성).
- 서비스마다 함께 필요한 액션이 있고 리소스 단위 제한이 되는지도 서비스별로 달라요. 그래서 **권한을 한 번에 맞게 설계하기는 거의 불가능**해요.
- 권한이 부족하면 요청이 오지만 **남는 권한은 아무도 알려주지 않아요.** 클릭옵스로는 최소 권한을 유지하기가 매우 부담스러워요.
- **권고**: 고객 보고 시 "IaC는 운영 환경 권한 설계에서 굉장히 중요한 역할을 한다"는 메시지로 필요성과 시급성을 강조해 주세요.

### 3.2 관리형, CMP, 인라인 중 무엇을 쓸지 판단하는 기준

| 구분 | 권고 |
|---|---|
| 도입 초기 | 관리형 정책으로 시작하고, 리소스 단위 제한이나 예외가 필요한 부분만 인라인으로 보완 |
| CMP 전환 기준 | **같은 인라인이 2~3개 권한세트에서 쓰이면 CMP로 전환**. 인라인은 권한세트당 1개, 크기 제한, 여러 곳을 손으로 고치다 보면 드리프트가 생김 |
| 코드로 관리할 때 | 코드에서는 정책 파일 하나를 여러 권한세트에 쓸 수 있어 위험이 줄어듦. 전환 기준을 더 높게 잡아도 됨 |
| CMP 중심 구조 | **ViewOnly/ReadOnly를 기본으로 깔고 생성·수정·삭제 권한만 CMP로 추가**하면 관리하기 편함 |

### 3.3 ViewOnlyAccess와 ReadOnlyAccess 구분

- **ViewOnly**: 설정 정보만 볼 수 있어요. 예를 들어 S3 버킷과 객체 목록은 보이지만 내용은 볼 수 없어요.
- **ReadOnly**: 데이터까지 읽을 수 있어요. 예를 들어 S3 객체를 다운로드할 수 있어요.
- 개인정보가 있는 S3에 ReadOnly를 주면 **개인정보 처리자에 해당할 수 있어요.** 기밀 데이터가 있는 계정은 ViewOnly로 시작해요.
- 현재 개발자에게 S3 ReadOnly를 줘서 다운로드가 가능한 문제가 있어요. ViewOnly 도입을 제안할 근거가 돼요.

### 3.4 공통 예외와 숨은 의존 권한

- 공통으로 막아야 할 것은 **SCP**(우선)나 퍼미션 바운더리로 처리해요. 현장에서는 SCP나 명시적 Deny를 주로 써요.
- **숨은 의존 권한 예시**
  - `iam:PassRole`: Lambda, CloudFormation, EC2를 만들 때 필요해요. **Resource를 `*`로 열지 말고 프리픽스로 제한**해요. 권한 상승 경로가 될 수 있어요.
  - KMS로 암호화된 리소스(S3, RDS, Secrets Manager 등)를 읽고 쓸 때는 KMS 키 권한도 함께 필요해요.
  - Glue는 스크립트를 S3에 저장하므로 S3 읽기·쓰기 권한이 필요해요.
  - `iam:CreateServiceLinkedRole`: 서비스를 처음 활성화할 때 필요해요.
- **찾는 방법**: 관리형 정책 중 "이게 왜 들어 있지?" 싶은 액션을 참고해요. 그다음 **개발 환경에서 테스트로 검증**한 뒤 운영 환경에 적용해요.
- **권장 절차**: 서비스팀이 개발 환경 기준으로 초안을 만들고 → 보안팀이 리뷰·승인하고 → 운영 권한세트에 적용해요.

### 3.5 멀티 계정에서 CMP 배포와 보호

- CFCT(Customizations for Control Tower)가 있으면 CFCT로 배포해요.
- 없으면 **CloudFormation StackSets로 OU를 대상으로 배포**해요. 새로 추가되는 계정에도 자동으로 배포돼 누락을 막아요.
- 배포한 뒤에는 개발자가 CMP를 수정할 위험이 있어요. **CMP에 프리픽스 규칙을 두고, 지정 역할 외에는 SCP로 수정을 금지**해요.
- 위협 시나리오(무엇이 걱정인지)에서 출발해 차단이나 탐지 방법을 설계하는 접근을 권해요. 고객 담당자와 브레인스토밍해서 시나리오를 더 찾아보세요.

### 3.6 IAM 역할 생성 위임과 권한 상승 차단

- **퍼미션 바운더리 패턴**: 개발자에게 IAM 역할 생성 권한을 줄 때 **바운더리 부착을 Condition으로 강제**해요. 바운더리에는 로그, 주요 DB, CloudTrail 삭제와 IAM 변경 금지를 넣어요. 바운더리 자체를 바꾸지 못하게 SCP로 막아요.
- **권한세트 사용자가 다른 역할로 AssumeRole하는 것 차단**: 권한세트로 들어온 사용자가 이미 있는 Admin 역할을 AssumeRole하면 권한이 상승해요. Condition에 `AWSReservedSSO_*` principal 프리픽스를 넣어 Deny해요. SA가 JSON 예시를 공유할 예정이에요.
- (참고) 금융권은 IaC가 없을 때 **운영 환경 IAM 생성 권한을 보안팀이 직접 갖기도** 해요. 보안팀 부담이 커서 고객사는 채택하지 않을 것으로 보여요.

### 3.7 KMS 키 접근 범위

- 고객 현황: 키는 계정별로 관리하고 태그는 쓰지 않아요.
- 모범사례는 태그 기반 ABAC예요. 다만 **태그가 빠지는 구멍**이 생길 수 있어 SCP 강제나 Config 커스텀 룰로 태그를 점검해야 해요.
- **권고**: 계정과 리소스 단위로 경계가 명확하다면 **리소스(프리픽스) 단위로 범위를 정하는 쪽**이 운영에 유리해요. ABAC를 같이 쓰는 것은 운영 부담을 감수할 수 있을 때만 해요.

### 3.8 Secrets Manager와 운영 환경 통제

- 운영 환경 시크릿은 워크로드가 쓰는 것이에요. 사람이 상시로 접근할 필요는 거의 없어요.
- API 키 갱신 같은 작업은 IaC로 하는 게 권고예요. 그게 어려우면 **승인을 받아 인프라팀이나 보안팀이 수행**해요.
- 고객사는 인프라 담당자가 대기 시간 문제로 직접 처리하는 문화라 역할을 나누기 어려워요. 그래도 **운영 환경 시크릿 조회를 개발자에게 상시 권한으로 줄지는 반드시 검토**해야 해요. SA 의견은 보안 쪽에 무게를 두라는 것이었어요.
- SCP로 운영 환경에서 권한세트를 통한 시크릿 읽기를 막는 방안도 검토해요.

### 3.9 사후 탐지와 자동 대응

- GuardDuty는 **탐지만** 해요. 사후 대응은 고객이 구성해야 해요.
- 예: EventBridge로 GuardDuty 탐지 결과를 받으면 해당 인스턴스의 보안그룹을 자동으로 격리해요.
- KMS 키 정책 변경이나 주요 시크릿 변경 같은 이벤트는 Config나 EventBridge로 모니터링해요.
- 침해 대응(IR) 시나리오별 **플레이북과 자동화**를 구성하면 임시 권한 상승이 필요한 상황이 줄어요.

### 3.10 긴급 접근(JIT, Break-glass)

- IaC를 쓰더라도 **운영 배포 때마다 롤백 계획**을 갖춰 클릭옵스로 들어가는 상황을 줄여요.
- **긴급용 권한세트**를 미리 설계해 두고, 고객사 승인 시스템과 API로 연동해 **기간을 정해 할당**해요. **세션은 1시간 정도로 짧게** 잡아요(개발 환경은 길게).
- (선택) SSO나 IdP, Direct Connect 장애에 대비해 **관리 계정에 Break-glass IAM 유저**를 둬요. 상위 승인권자의 MFA를 붙이고, 멤버 계정에는 이 유저만 AssumeRole할 수 있는 역할을 배포해요. 장애에 민감한 고객사에서 쓰는 방식이에요.

### 3.11 권한세트 구분 단위와 지속 관리 도구

- 직무 단위 구분은 적절해요. 여기에 **환경 단위 구분도 필수**예요. 개발 권한이 그대로 운영으로 가면 안 돼요.
- **IAM Access Analyzer**: 외부 접근 분석은 무료이고, 미사용 권한 분석은 유료예요. 무료 기능부터 써 보는 걸 권해요. Tenable이나 Wiz와 비슷하지만 AWS 서비스라서 숨은 권한을 더 정확히 식별할 것으로 보여요.
- IaC를 도입한 뒤에는 **파이프라인에 Access Analyzer나 Checkov, Trivy를 연동**해요. IAM 리소스가 바뀌면 보안 승인을 거치게 해요.
- SageMaker와 Bedrock은 숨은 권한이 많아요. 서비스별 액션과 의존 권한을 리서치해서 정리해야 해요.

## 4. 회의 후 내부 논의 (SA 퇴장 후)

- **AWS ProServe(Nova) 팀 현황**
  - AI DevOps 도구를 개발하고 PoC를 하고 있어요. 테라폼으로 리소스를 직접 만들고 지우는 일이 잦아요.
  - 현재 **Admin 권한세트를 사용**하고 있어요(안티패턴인 것은 인지하고 있어요).
  - 승인이 **11월 말까지**라서 12월부터 개편된 권한세트가 적용될 예정이에요(확정 여부는 확인 필요).
- **As-Is 분석의 한계**: Bedrock Admin 등 분리된 것처럼 보이는 권한세트도 실제로는 Admin 수준이에요. 실제로 어떤 액션을 쓰는지 파악할 수단이 없어요.
- **Secrets Manager 사용 사례**: Aurora PostgreSQL 접속 정보를 조회하는 데 써요. Delete 같은 액션은 실제로는 거의 쓰지 않을 것으로 보여요. DBA 역할을 하는 사람은 생성과 설정 권한이 필요할 수 있어요.
- **요구사항 충돌**
  - TA: 권한세트를 바꿔 타지 않고 **하나의 권한세트로 직무 업무를 끝낼 수 있게** 해 달라는 요구예요(편의성).
  - 고객 매니저: 외부 협력사에 넓은 권한을 주기 부담스러우니 **업무 영역별로 권한세트를 나누자**는 요구예요(통제).
- **CMP 활용 방식에 대한 우려**: 고객 매니저는 직무명 CMP(예: AI-DevOps-Developer)에 인라인 내용을 **통째로 옮겨** IaC로 관리하는 방식을 고려하고 있어요. 이렇게 하면 CMP 하나가 비대해지고 같은 권한이 여러 CMP에 중복돼요.
- 개발 환경은 속도가 우선이라 권한을 지나치게 막으면 "권한세트 개편이 의미 없다"는 반발이 나올 수 있어요.

| 1 | 정책 우선순위를 **관리형 → CMP → 인라인**으로 하는 원칙은 SA 권고와 일치해요 |

| 4 | 운영 환경 Secrets Manager는 **상시 권한을 빼고 승인 기반**으로 하는 방향을 권고안에 넣어요 |
| 5 | IaC가 없는 동안에는 **CMP를 StackSets로 배포하고 SCP로 보호**하는 방안을 대안으로 제시해요 |

## 6. 의사결정 필요 사항 (고객)

| # | 안건 | 제안 방향 | 결정 주체 |
|---|---|---|---|
| D1 | 편의성(TA)과 통제(협력사 권한 제한) 중 무엇을 우선할지 | 개발 환경은 편의성 + 가드레일, 운영 환경은 통제 우선 | 고객 권한 담당 매니저, TA |
| D2 | CMP 구조를 직무별 단일 CMP로 할지, 기능 모듈 CMP 조합으로 할지 | 기능 모듈 조합 + 직무별 예외만 인라인 | 고객 권한 담당 매니저 |
