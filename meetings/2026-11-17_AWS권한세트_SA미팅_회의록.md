## 1. 요약

* 운영 환경 최소 권한 설계는 IaC가 전제이며, IaC 부재 시 CMP는 StackSets 배포 + SCP 보호로 대체
* 정책 우선순위는 Managed(ViewOnly/ReadOnly) → CMP → Inline 순으로 적용
* Secrets Manager/KMS는 운영 환경 상시 권한 제외, 승인 기반 JIT로 부여
* 12월 개편 예정에 따라 TA(편의성)와 고객 매니저(협력사 통제) 간 요구사항 조율 필요

---

## 2. 배경

* 권한세트는 클라우드 포탈을 통해서만 부여되며, 포탈 기반 권한세트 표준화 및 부여 절차 간소화 목적
* As-Is는 Inline 정책 및 AdministratorAccess 위주로 구성되어 변경 관리에 어려움 존재
* 관리자 권한세트에 KMS, Secrets Manager 등 보안 서비스 권한이 포함된 상태
* Control Tower 기반 멀티 계정 운영 중이며, IaC는 미적용(테라폼 도입 검토 단계)
* 보안팀은 권한세트 작업에 미관여

---

## 3. 주요 논의 내용

### IaC 필요성

* 운영 환경 쓰기 권한 자체가 장애 리스크이며, 서비스별 의존 액션 및 리소스 제한 가능 여부가 상이하여 1회 설계로 최소 권한 달성은 어려움
* ClickOps 환경에서는 불필요 권한 식별이 어려워 최소 권한 유지 부담이 큼
* 고객 보고 시 IaC가 운영 환경 권한 설계의 핵심 축이라는 메시지로 시급성 강조 필요

### 정책 유형 선택 기준

* 도입 초기에는 Managed로 시작하고, 리소스 제한 및 예외 사항만 Inline으로 보완
* 동일 Inline이 2~3개 권한세트에서 사용될 경우 CMP로 전환(휴먼 에러 및 드리프트 방지 목적)
* 코드로 관리할 경우 정책 파일 재사용이 가능하여 전환 기준 상향 가능
* ViewOnly/ReadOnly를 기본으로 두고 생성·수정·삭제 권한만 CMP로 추가하는 구성 권고

### ViewOnly / ReadOnly 구분

* ViewOnly는 설정 정보 조회까지, ReadOnly는 데이터 조회(S3 객체 다운로드)까지 가능
* PII 등 기밀 데이터가 있는 계정은 ViewOnly로 시작 권고(개인정보 처리자 해당 여부 기준)
* 현재 개발자 S3 ReadOnly로 다운로드가 가능한 상태로, ViewOnly 제안 근거로 활용 가능

### 공통 예외 및 숨은 의존 권한

* 공통 차단은 Permission Boundary보다 SCP 또는 명시적 Deny 위주로 적용
* iam:PassRole은 Resource를 프리픽스로 제한하여 권한 상승 경로 차단
* KMS 암호화 리소스 접근 시 KMS 키 권한, Glue 사용 시 S3 권한, 서비스 최초 활성화 시 CreateServiceLinkedRole 권한 필요
* 숨은 권한은 Managed 정책 참고 후 개발 환경 테스트로 검증하고 운영에 적용
* 서비스팀이 개발 환경 기준 초안 작성, 보안팀이 리뷰·승인 후 운영 적용하는 절차 권고

### 멀티 계정 CMP 배포 및 보호

* CFCT 운영 시 CFCT로 배포, 미운영 시 CloudFormation StackSets로 OU 대상 배포(신규 계정 자동 배포)
* 배포된 CMP는 프리픽스 규칙 적용 후 SCP로 지정 역할 외 수정 금지
* 위협 시나리오 기반으로 차단·탐지 방안을 설계하고, 고객 담당자와 시나리오 추가 발굴 필요

### IAM 역할 생성 위임 및 권한 상승 차단

* IAM 역할 생성 권한 부여 시 Permission Boundary 부착을 Condition으로 강제하고, Boundary 수정은 SCP로 차단
* 권한세트 사용자가 기존 Admin 역할을 AssumeRole하는 권한 상승 방지를 위해 AWSReservedSSO_* 프리픽스 기반 Deny 적용(SA JSON 예시 공유 예정)
* 금융권은 IaC 부재 시 운영 IAM 생성 권한을 보안팀이 직접 보유하는 사례 존재(고객사는 미채택 예상)

### KMS 키 접근 범위

* 현재 계정별 키 관리, 태그 미사용 상태
* BP는 태그 기반 ABAC이나, 태그 누락 시 통제 공백 발생 가능
* 계정·리소스 단위 경계가 명확하므로 리소스(프리픽스) 단위 범위 지정 권고

### Secrets Manager 및 운영 통제

* 운영 시크릿은 워크로드 사용 목적으로, 사람의 상시 접근 필요성은 낮음
* 키 갱신 등 작업은 IaC 또는 승인 기반으로 인프라·보안팀이 수행하도록 역할 분리 권고
* 고객사는 인프라 담당자가 직접 처리하는 문화로 분리가 어려우나, 운영 시크릿 상시 조회 권한 부여 여부는 반드시 검토 필요
* 운영 환경 권한세트를 통한 시크릿 조회는 SCP 차단 검토

### 사후 탐지 및 자동 대응

* GuardDuty는 탐지 기능만 제공하며, 사후 대응은 고객 구성 필요
* EventBridge 기반 자동 대응(예: 침해 인스턴스 SG 격리) 및 KMS 키 정책·시크릿 변경 이벤트 모니터링 권고
* IR 시나리오별 플레이북 및 자동화 구성으로 임시 권한 상승 필요 상황 최소화

### 긴급 접근(JIT / Break-glass)

* IaC 적용 시에도 운영 배포 건별 롤백 계획 수립으로 ClickOps 접근 최소화
* 긴급용 권한세트를 사전 설계하고, 고객사 승인 시스템과 API 연동하여 기간 한정 할당
* 임시 권한 세션은 1시간 수준으로 짧게 설정
* (선택) SSO/IdP 장애 대비 관리 계정 Break-glass IAM 유저 운영(상위 승인권자 MFA 적용)

### 권한세트 구분 및 지속 관리

* 직무 단위 구분에 더해 환경 단위 구분 필수(개발 권한의 운영 이관 금지)
* IAM Access Analyzer 활용 권고(외부 접근 분석 무료, 미사용 권한 분석 유료)
* IaC 도입 후 파이프라인에 Access Analyzer, Checkov, Trivy 연동하여 IAM 변경 시 보안 승인 적용
* SageMaker, Bedrock은 숨은 권한이 많아 서비스별 리서치 필요
* 최소 권한은 일회성이 아닌 지속 운영 활동이라는 점을 고객에게 전달 필요

## 4. 회의 후 내부 논의

* ProServe(Nova) 팀은 PoC 성격으로 테라폼 기반 리소스 생성·삭제가 잦으며, 현재 Admin 권한세트 사용 중
* Admin 권한 승인은 11월 말까지이며, 12월부터 개편 권한세트 적용 예정(확정 여부 확인 필요)
* As-Is 권한세트가 실질적으로 Admin 수준이라 실사용 액션 파악이 어려운 상태
* Secrets Manager는 Aurora PostgreSQL 접속 정보 조회 목적으로 사용되며, Delete 등은 미사용 추정
* TA는 단일 권한세트로 직무 업무 완결을, 고객 매니저는 협력사 대상 업무 영역별 분리를 요구하여 조율 필요
* 고객 매니저는 직무명 CMP에 Inline 내용을 일괄 이관하는 방식을 검토 중이나, CMP 비대화 및 중복 우려 존재
* 개발 환경은 속도가 우선이라 과도한 제한 시 개편 실효성 문제 제기 가능성 존재
